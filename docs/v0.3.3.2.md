# v0.3.3.2 — Density and progressive disclosure

## Audit and design (before implementation)

Production baseline a2d3e61, Chrome at 390 × 844, installation SF/TEP league. Observed initial document heights: Home 1415px, Waivers 9232px (13 recommendation cards, 2152 DOM nodes, first card at 770px), Signals 6797px (20 cards, 273 nodes, first at 485px), League 957px, Players 2397px (15 cards), More 1530px. Lineup was 1368px while optional context was still loading; this is not a settled analytics comparison.

The 150px account panel, repeated waiver explanations/metadata, fully mounted hidden player analytics, repeated same-player signal cards and unconditional default player results create avoidable length. Home and League need little change; More remains the deliberate full management destination.

Plan: five initial waiver recommendations in the existing model order, Show more increments of five, all returned candidates reachable. Keep category/position selection; do not create model categories. Compact summaries retain rating, net gain, legal transaction, evidence coverage and availability caveats. Put components, detailed history, replacement and source evidence in lazy disclosures. Group signals by player after filtering, sort for presentation using existing severity/confidence, own-roster/eligibility relevance, through-week and within-family dimensionless movement, preserving every returned signal in details. Show five player groups initially. Compact roster summaries with expandable groups and analytics. Search-first Players, explicit shortcuts, compact results. One-line league/season switcher outside More. No additional sticky headers.

No changes to lib/, API routes, model weights, signal generation, sources, archive semantics or schemas. UI ordering never changes scores. Tests must verify bounded initial DOM, expandable evidence, value fidelity, same-player grouping, state isolation, existing navigation/account flows and mobile clearance.

## Implemented behavior

- Waivers: five initial cards, five more per click, original category order and exact existing values. No new classifications. All Available retains its separate position-filtered pages. API-truncated candidates remain explicitly disclosed, not falsely described as a complete NFL catalog.
- Signals: five player groups, five more per click. Records are filtered before grouping, never deduplicated away. Sort keys are existing severity (critical/high/notable/context), confidence, own optimized starters then known fantasy eligibility, through-week, signal family, and absolute movement within that same family. Family ordering makes the comparison transitive and avoids comparing different units. Unknown values sort last. Each group's primary is its highest-priority returned record; expanded records preserve full warnings, explanation, provenance and IDs. This is display priority, not a football score.
- Reusable `ExpandableDetail` uses a button with aria-expanded/aria-controls and lazily mounts its body. Open states are scoped by league, stable user ID, roster, season and item. `CompactPlayer` / `PlayerSummary` show identity, StartValue, opponent and injury flags first; production/opportunity context remains available on expansion. Native deep disclosures remain for raw evidence.
- Starter and bench groups initially expand; IR/taxi initially collapse with counts. All groups can collapse. Search results reuse compact rows; Players initially mounts zero results until a search/filter/explicit browse choice. No new ranking is invented for search shortcuts.
- Account controls collapse to league/season plus Switch on primary routes; More opens full management. Existing error alerts, injuries, partial-scoring and small-sample caveats remain visible. General waiver methodology/coverage notes collapse; detailed source/model warnings remain in the existing evidence panels. Existing Home warnings and critical load errors retain their prior semantics.
- Category/search filters, visible limits and expanded cards survive client navigation. Visible limits are league/category-scoped. Disclosure states are also account/roster/season-scoped. Full reload resets view state, while existing browser-local account preferences and player URLs persist. No new requests are triggered by opening evidence.

## Measurements and validation

Settled mobile comparison at 390 × 844 using the same installation league, with decision context loaded before route measurements:

| View | Before height / DOM nodes / cards | After height / DOM nodes / cards |
| --- | --- | --- |
| Waivers | 9232px / 2154 / 13 | 1778px / 188 / 5 |
| Signals | 6797px / 275 / 20 | 1612px / 148 / 5 player groups |
| Lineup | 3402px / 2309 / 1 roster | 2945px / 246 / 1 roster |
| Players | 3586px / 279 / 15 | 844px / 114 / 0 |

The new lineup initially exposes bench rows too; despite that, its document is shorter and its DOM is about 89% smaller. Deep analytics are mounted only when requested. Measurements depend on live player names, signals and injury notices and are not fixed performance guarantees. No CPU/hydration timing claim is made. API payload size remains unchanged. First Load JS is 112kB Home, 113kB Signals, 116–118kB data-heavy routes: a small bundle increase buys bounded initial rendering.

The suite adds two pure presentation tests and seven browser tests to the existing coverage. It verifies exact rating fidelity, immutable input records, signal grouping without record loss, unit-correct summary trends, Show more, lazy details, keyboard disclosure, cross-league state isolation, search-first behavior, all routes/account flows and expanded-content clearance at 320/375/390/414px. Physical iOS devices remain untested; safe-area CSS and viewport handling are retained.

The existing decision-basis safeguard can request Refresh if live league data changes between snapshot and decision loads. This release preserves that warning and does not weaken synchronization checks.
