# v0.4 — Trade Engine (design specification, first wave)

Status: **proposed** (planning PR, not implemented; repository-owner decisions of 2026-09-25 applied). Architecture rationale: `docs/decisions/0001-trade-engine-architecture.md`. Execution state: `TASKS.md` (V04-01 … V04-03). Rules: `AGENTS.md`. Product constraints: `PROJECT_SPEC.md` → *v0.4 planning constraints*.

## Scope of the first wave

In scope: a pure, provider-independent **trade evaluator** that takes one explicit proposal between exactly two rosters (1–2 players sent by each side) and reports what it does to each roster's legal lineup and depth, under a stated horizon, with every unknown disclosed. Plus an independent adversarial test suite.

Out of scope for the first wave: candidate generation/trade search (V04-03, design only), HTTP endpoints, UI, chat routes, draft-pick or FAAB assets, three or more assets from one side, empty-side transfers, three-team/multi-team trades, caller-selected forced drops, any combined "trade score" or fairness verdict, acceptance probabilities, Market Value, ROS/dynasty valuation, provider writes.

## Valuation horizon

Every evaluation carries an explicit `horizon` object (id, value source, calibration status, limitations). Owner decision: `next_game` is the only first-wave horizon.

- **`next_game`** (supported): lineup values from `start_value.central`, with the same availability filter as add/drop (`unavailableThisWeek`, `no_scheduled_game`). Byes and injuries make this horizon deliberately narrow; the output says so.
- Depth/scarcity uses Q-based VOR labeled **descriptive quality**, not a horizon forecast (same as add/drop today).
- Any other requested horizon (`rest_of_season`, `dynasty`, multi-week) → `UNSUPPORTED_HORIZON`.
- The three-week acquisition estimate (`pickup_value`) is **not** used as trade, multi-week or ROS value.

## Proposed contracts (`trade-1`, name provisional; finalized in V04-01 phase A)

**TradeContext** (built by `lib/trade/context.js` from a normalized snapshot **and** the decision-support 0.3 output for the same basis — `decisionBasis(snapshot) === decision.basis`, else `STALE_BASIS`):

- `basis`, `provider`, `identity` (mode and resolved/selected roster exactly as supplied; never inferred), `capabilities` (explicit input; missing ⇒ every gated feature unsupported).
- `league`: starter slots (excluding `BN`/`IR`/`TAXI`), active capacity (non-`IR`/`TAXI` positions, as add/drop), reserve/taxi slot counts and open slots with `verified` flags, team count, scoring profile (Superflex, TE premium), unsupported slots/rules.
- `rosters`: id, owner id, players with eligibility, `active|reserve|taxi` status and reserve/taxi placement eligibility (`verified` or `unknown`; never derived from injury status).
- `values`: per player `{next_game, quality, vor, vor_position, supported, schedule_status, injury_status}`, `null` where unknown.
- `replacement`: per-position levels as produced by the decision engine.

**TradeProposal**: `{ sides: [{ roster_id, sends: [{ type: "player", id }] }, { … }], horizon: "next_game" }`. Exactly two distinct rosters; each side sends 1 or 2 players (1-for-1, 2-for-1, 1-for-2, 2-for-2). Empty sides ⇒ `EMPTY_SIDE`; 3+ assets from one side ⇒ `PACKAGE_TOO_LARGE`; more than two rosters ⇒ `UNSUPPORTED_TRADE_SHAPE`.

**TradeEvaluation** (output):

- `schema_version`, `model_version` (decision engine version consumed), `basis`, `horizon`, `status: evaluated | invalid | unsupported | withheld` (a side's forced drops may be `blocked` or `undetermined` within an evaluated result), `errors[]` (code, asset, message).
- `sides[]` per roster: `sends`, `receives`, `before` / `after` (legal lineup, starter total, active count vs capacity, positional positive-VOR counts vs starter demand), `forced_drops` (`required` count, dropped player ids, `status: none | selected | blocked | undetermined`, evaluated combination count), `reserve_placement` (per acquired player: `active` or verified `reserve`/`taxi`, with the limitation when unverified), `starter_change` (signed or `null`), `depth_change` (signed or `null`), `unknowns[]`, `warnings[]`.
- `market_value: null`. No acceptance probability, fairness verdict, winner label or combined score.

Error codes (initial): `STALE_BASIS`, `UNKNOWN_ROSTER`, `SAME_ROSTER`, `EMPTY_SIDE`, `ASSET_NOT_OWNED`, `DUPLICATE_ASSET`, `UNSUPPORTED_ASSET`, `UNSUPPORTED_HORIZON`, `PACKAGE_TOO_LARGE`, `UNSUPPORTED_TRADE_SHAPE`, `UNSUPPORTED_SLOTS`, `CAPACITY_UNKNOWN`, `OVER_CAPACITY_BEFORE`, `FORCED_DROP_BLOCKED`.

## Evaluation semantics

1. **Validate** the whole package before computing: rosters exist and differ; every asset exists, is owned by its sending roster at this basis, and appears once; asset types are supported; horizon supported. Any failure ⇒ `invalid`/`unsupported`, no partial valuation.
2. **Apply** the package to copies of both rosters. An acquired player uses reserve/taxi capacity **only** when normalized provider data verifies all three: an open slot, the player's eligibility for it, and the provider capability (`IR` / `taxiSquads`). Otherwise the player counts against active capacity and the reserve-placement limitation is reported. Injury status alone never places a player on IR.
3. **Capacity**: if a roster was over active capacity before the trade ⇒ `withheld` (mirrors add/drop). If over capacity after ⇒ it needs `k` forced drops.
4. **Forced drops** (owner-approved, automatic): candidates are post-trade active players that are legally droppable and not protected by the existing add/drop protections. Evaluate every `k`-combination; prefer the one with the strongest post-drop legal starting lineup (Hungarian starter total at the horizon), then the most preserved positive bench VOR (existing VOR semantics), then a stable player-id order solely for determinism. No new weights or trade-specific drop score. Dropped players are returned explicitly. Fewer than `k` candidates ⇒ side `blocked` (`FORCED_DROP_BLOCKED`); a protected player is never dropped. If unknown values make the comparison undefined ⇒ side `undetermined`, no silent choice. With the 1–2 player cap and no over-capacity start, `k ≤ 2` (e.g. a side sends one reserve/taxi player, which frees no active slot, and receives two players placed active). Caller-selected drops are a future extension.
5. **Lineups**: `optimizeLineup` before and after for each side, same slot list and availability filter as add/drop.
6. **Starter change** = after − before starter total; `null` if any usable player compatible with an open/affected slot has unknown horizon value, or a relevant game has kicked off (lock unverified).
7. **Depth change** = change in summed positive VOR of unassigned active players; `null` if any player whose membership changes (traded or forced-dropped) has unknown VOR. Unknowns are never counted as zero.
8. **Positional context**: before/after positive-VOR counts vs `eligible_starter_demand` per position (Superflex QB demand, TE premium via scored values, dual eligibility at best single VOR). Context only; no weight.
9. Components are reported separately per roster. Owner decision: no combined fairness score and no winner/loser verdict; a future combined policy (e.g. anything like add/drop's `0.25/0.10` net formula) needs its own design and validation.

## Assets and capabilities

- First wave supports `player` assets only. `draft_pick` and `faab` ⇒ `UNSUPPORTED_ASSET` with the capability reason. Pick holdings from Sleeper are transaction-history based, so pick ownership and pick values are not inferred.
- Provider-specific facts enter only through `TradeContext`; `lib/trade/*` imports no provider transport, no `lib/sleeper.js`, no `lib/derive.js`.
- ESPN live remains disabled; the evaluator works on an injected offline ESPN context in tests only.
- Signals, market attention and Sleeper add-interest are not read by the evaluator. Pickup Rating is unchanged.

## Computation and delivery

The evaluator is a pure function over an in-memory `TradeContext`; one evaluation runs at most 4 lineup optimizations plus one lineup optimization per forced-drop combination (`k ≤ 2`, so at most `C(n,2)` for `n` droppable players). Nothing is added to `/api/decision-support`, `/api/snapshot` or `/api/chat/*` in the first wave. A later, separately approved task may add a lazy GET endpoint with its own schema (no persistence, identity-keyed cache).

## Test matrix (owner of coverage)

| Case | V04-01 core unit tests | V04-02 adversarial suite |
|---|---|---|
| 1-for-1, 2-for-1, 1-for-2, 2-for-2 | basic | both sides, lineup reassignment |
| Out-of-scope shapes (3+ from a side, empty side, 3 rosters) | error codes | crafted proposals |
| Forced drops for uneven packages | selection rule, tiebreaks, explicit output | protected-only rosters, blocked, undetermined, ties |
| Superflex QB scarcity | ✓ | 10-team SF/TEP synthetic fixture |
| TE-premium scarcity | ✓ | 10-team SF/TEP synthetic fixture |
| Dual-position players | one slot, best single VOR | swaps that change which slot they fill |
| Injured / reserve / IR / taxi | verified placement only | open slot but unverified eligibility, missing capability, injured player not auto-IR'd, traded reserve players |
| Missing player values | `null` propagation | unknowns on each side, cancellation of untouched unknowns |
| Uneven roster sizes / over-capacity | ✓ | before-trade over capacity |
| Incomplete assets (picks, FAAB) | error codes | capability combinations |
| Ownership / duplicates / same roster | ✓ | stale basis, crafted proposals |
| Spectator vs selected roster | no inferred "mine" | identity modes |
| Provider capability gaps | ✓ | ESPN offline context, missing capabilities |
| League formats | — | 10-team Superflex/TE premium and 12-team full PPR, **synthetic** fixtures modeled on those structures |

Fixtures are synthetic and labeled as such; no private league data is committed. No test claims live validation.
