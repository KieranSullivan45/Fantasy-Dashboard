# v0.4 — Trade Engine (design specification, first wave)

Status: **proposed** (planning PR #2, not implemented; repository-owner decisions of 2026-09-25 applied; revised after the Codex review of PR #2). Architecture rationale: `docs/decisions/0001-trade-engine-architecture.md`. Execution state: `TASKS.md` (V04-01 … V04-03). Rules: `AGENTS.md`. Product constraints: `PROJECT_SPEC.md` → *v0.4 planning constraints*.

## Scope of the first wave

In scope: a pure, provider-independent **trade evaluator** that takes one explicit proposal between exactly two rosters (1–2 players sent by each side) and reports what it does to each roster's legal lineup and depth, under a stated horizon, with every unknown disclosed. Plus an independent adversarial test suite.

Out of scope for the first wave: candidate generation/trade search (V04-03, design only), HTTP endpoints, UI, chat routes, draft-pick or FAAB assets, three or more assets from one side, empty-side transfers, three-team/multi-team trades, caller-selected forced drops, any combined "trade score" or fairness verdict, acceptance probabilities, Market Value, ROS/dynasty valuation, provider writes, and the production wiring that supplies authoritative protection evidence from the server's internal decision contexts (a later, separately scoped task; see *Authoritative drop-protection evidence*).

## Valuation horizon

Every evaluation carries an explicit `horizon` object (id, value source, calibration status, limitations). Owner decision: `next_game` is the only first-wave horizon.

- **`next_game`** (supported): lineup values from `start_value.central`, with the same availability filter as add/drop (`unavailableThisWeek`, `no_scheduled_game`). Byes and injuries make this horizon deliberately narrow; the output says so.
- Depth/scarcity uses Q-based VOR labeled **descriptive quality**, not a horizon forecast (same as add/drop today). Replacement levels are taken from the value source and held fixed for both before and after states.
- Any other requested horizon (`rest_of_season`, `dynasty`, multi-week) → `UNSUPPORTED_HORIZON`.
- The three-week acquisition estimate (`pickup_value`) is **not** used as trade, multi-week or ROS value.

## Proposed contracts (`trade-1`, name provisional; finalized in V04-01 phase A)

**TradeContext** is built by `lib/trade/context.js` from three inputs: (1) a normalized snapshot; (2) the decision/value source for the same basis (decision-support 0.3 output or the equivalent internal decision result: values, replacement levels, model/feature versions); (3) **authoritative drop-protection evidence** (below). Fields:

- `basis`, `provider`, `identity` (mode and resolved/selected roster exactly as supplied; never inferred), `capabilities` (explicit input; missing ⇒ every gated feature unsupported), `versions` (`model_version`, `feature_version` of the consumed value source).
- `league`: id, season, week / as-of week, starter slots (excluding `BN`/`IR`/`TAXI`), active capacity (non-`IR`/`TAXI` positions, as add/drop), reserve/taxi slot counts and open slots with `verified` flags, team count, scoring profile (Superflex, TE premium) and scoring identity where available, unsupported slots/rules.
- `rosters`: id, owner id, players with eligibility, `active|reserve|taxi` status and reserve/taxi placement eligibility (`verified` or `unknown`; never derived from injury status).
- `values`: per player `{next_game, quality, vor, vor_position, supported, schedule_status, injury_status}`, `null` where unknown.
- `replacement`: per-position levels as produced by the decision engine.
- `protection`: per active player on either roster, `{ player_id, evidence: "sufficient" | "insufficient", protected: true | false | null, reasons[], droppable: true | false | null, provenance: { producer, population: "full_internal_contexts", provider, league_id, season, week, model_version, feature_version } }`. `protected`/`droppable` are `null` whenever `evidence` is `insufficient`.

### Context validation (two distinct checks, both before evaluation)

1. **Existing decision basis — unchanged.** `decisionBasis(snapshot) === decision.basis` (`lib/decision/basis.js`); otherwise `STALE_BASIS`. The basis contract is not modified.
2. **Trade-local context validation — additional.** Basis-string equality is not treated as sufficient. `lib/trade/context.js` compares the normalized metadata of the snapshot, the value source and the protection evidence: provider identity; league identity; season; week / as-of week; roster/team identity for both proposal sides; identity mode and selected roster where `selected_roster` applies; normalized `roster_positions` / lineup configuration; scoring/context identity where available; consumed `model_version` and `feature_version`. Any mismatch, or a required field absent from one source, ⇒ `CONTEXT_MISMATCH` (field named) and no evaluation. This is trade-local: no public schema (snapshot 0.2, decision-support 0.3, chat-1) changes to support it.

### Authoritative drop-protection evidence

- Evidence is produced by the existing add/drop protection logic in `lib/decision/add-drop.js`, run on the **same full internal inputs** it uses today (the full decision `contexts` map, league roster positions, player status, schedule status). Same reasons, thresholds and ordering.
- `lib/trade/*` never recomputes protection status and never derives it from the decision-support `player_context` subset (the upper-tier percentile and other evidence need the full population).
- Evidence is limited to what add/drop reads today, including the legacy `analytics.signals` role labels already used by the expanding-role protection. Signal Engine output (`signals-1`), market attention (`market-1`) and Sleeper add-interest/trending/popularity are not protection evidence and may not be added as such.
- Per player the evidence determines: **protected** (`protected: true`; never dropped — note that "Unknown asset value" is an existing protection, so a missing value with a present record is *sufficient* evidence of protection); **droppable** (`evidence: sufficient`, `protected: false`, `droppable: true`; a forced-drop candidate, legal under known roster rules only); **insufficient** (no record, provenance mismatch, or missing required inputs). Insufficient evidence is never treated as unprotected, and no forced drop is selected from it.
- **Supply boundary.** V04-01 adds a behavior-preserving exported helper in `add-drop.js` that exposes the existing protection results from the existing inputs (no change to reasons, thresholds, ordering, outputs or `transactionEvaluator` behavior). The V04-01 context builder accepts that helper's output as an input; V04-01 tests produce it by running the helper on full synthetic contexts. Wiring the helper to the server's internal contexts for a real caller (e.g. inside a future lazy trade endpoint) is a later task, because `build-context.js` is outside V04-01 scope. The evaluator contract requires authoritative evidence regardless of who supplies it.

**TradeProposal**: `{ sides: [{ roster_id, sends: [{ type: "player", id }] }, { … }], horizon: "next_game" }`. Exactly two distinct rosters; each side sends 1 or 2 players (1-for-1, 2-for-1, 1-for-2, 2-for-2). Empty sides ⇒ `EMPTY_SIDE`; 3+ assets from one side ⇒ `PACKAGE_TOO_LARGE`; more than two rosters ⇒ `UNSUPPORTED_TRADE_SHAPE`.

**TradeEvaluation** (output):

- `schema_version`, `model_version` / `feature_version` (consumed), `basis`, `horizon`, `status: evaluated | blocked | withheld | invalid | unsupported`, `errors[]` (code, asset/roster, message), `legality: "conditional_known_rules"` with the limitation that platform transaction locks/deadlines are unverified.
- `sides[]` per roster: `sends`, `receives`, `before` / `after` (legal lineup, `filled_starter_slots`, `starter_total`, bench membership, `depth_total`, active count vs capacity, positional positive-VOR counts vs starter demand; any undetermined part `null`), `forced_drops` (`required` k, `status: none | selected | blocked | undetermined`, `dropped` — sorted ids, `null` unless `selected` —, candidates, excluded players with reasons, evaluated combination count, `diagnostics[]`), `reserve_placement` (per acquired player: `active` or verified `reserve`/`taxi`, with the limitation when unverified), `starter_change` (signed or `null`), `depth_change` (signed or `null`), `unknowns[]`, `warnings[]`.
- `market_value: null`. No acceptance probability, fairness verdict, winner label or combined score.

Error codes (initial): `STALE_BASIS`, `CONTEXT_MISMATCH`, `UNKNOWN_ROSTER`, `SAME_ROSTER`, `EMPTY_SIDE`, `ASSET_NOT_OWNED`, `DUPLICATE_ASSET`, `UNSUPPORTED_ASSET`, `UNSUPPORTED_HORIZON`, `PACKAGE_TOO_LARGE`, `UNSUPPORTED_TRADE_SHAPE`, `UNSUPPORTED_SLOTS`, `UNSUPPORTED_DROP_COUNT`, `CAPACITY_UNKNOWN`, `OVER_CAPACITY_BEFORE`, `FORCED_DROP_BLOCKED`, `FORCED_DROP_UNDETERMINED`.

## Evaluation semantics

1. **Validate** the contexts (basis, then trade-local validation) and the whole package before computing: rosters exist and differ; every asset exists, is owned by its sending roster at this basis, and appears once; asset types are supported; horizon supported. Any failure ⇒ `invalid`/`unsupported`, no partial valuation.
2. **Apply** the package to copies of both rosters. Existing roster players are not re-slotted. An acquired player may use reserve/taxi capacity **only** when normalized provider data verifies all three: an open slot, the player's eligibility for it, and the provider capability (`IR` / `taxiSquads`). Otherwise the player counts against active capacity and the reserve-placement limitation is reported. Injury status alone never places a player on IR. If more eligible incoming players than verified open slots exist (e.g. two incoming players competing for one verified IR slot), placement is allocated **jointly**: each feasible allocation (distinct players to distinct verified slots, including leaving players active) is a separate candidate after-state, evaluated together with its forced-drop combinations under the ordering in step 5, with the canonical reserve-placed id sequence as a final key after the dropped-id sequence. Two players are never assumed to share one slot.
3. **Capacity**: if a roster was over active capacity before the trade ⇒ `withheld` (`OVER_CAPACITY_BEFORE`, mirrors add/drop). Otherwise `k = max(0, active_after − active_capacity)` forced drops are required for that side (per reserve allocation). **`k ≤ 2` is a derived invariant**, not a search limit: with no over-capacity start, `active_after = active_before − outgoing_active + incoming_active` and `incoming_active ≤ 2` under the first-wave package cap (e.g. a side sends one reserve/taxi player, freeing no active slot, and receives two players placed active). A context requiring `k > 2` violates the first-wave assumptions and returns `UNSUPPORTED_DROP_COUNT` (`unsupported`); the search is never truncated to two.
4. **Lineups and unknown values**: `optimizeLineup` for each roster state with the same slot list and availability filter as add/drop. Optimizer input is canonicalized (players sorted by canonical id, below) so equal-value solutions cannot vary bench membership or bench VOR between runs. A player is **lineup-relevant** in a state when usable (not `unavailableThisWeek`, not `no_scheduled_game`) and eligible for at least one starter slot; non-usable or slot-ineligible players cannot affect assignment. If any lineup-relevant player has `next_game: null`, that state's assignment, `starter_total` and bench membership are **undetermined** (`null`): an unbounded unknown value could move the player into or out of any slot it fits. `filled_starter_slots` stays determinable, since the maximum legal slot fill depends on eligibility, not value.
5. **Forced drops** (owner-approved, automatic): candidates are post-trade active players whose protection evidence is sufficient and `droppable: true`; protected players are never dropped. Every `k`-combination is evaluated and ranked by this **lexicographic** key, no scalar weights:
   1. filled legal starter-slot count — descending;
   2. legal starter-value total — descending;
   3. preserved positive bench VOR (sum of `max(0, VOR)` over post-drop bench, existing VOR semantics) — descending;
   4. canonical dropped-player-id sequence — ascending (strictly the final, determinism-only tiebreak).

   **Canonical id order** is deterministic and locale-independent: ids compared as strings by UTF-16 code units (JavaScript `<`/`>` on strings), never `localeCompare`, `Intl` or numeric parsing. Each drop set is sorted by that order before comparison; sequences compare element-wise.

   **Comparing with unknowns**: two combinations compare at the first key where they are not known-equal. If both values at that key are known, that key decides. If either is unknown, the comparison is undetermined — except at key 3, where the unknown contribution of a player on the bench in *both* combinations cancels (same player, same fixed VOR) and the known remainders are compared. Key 2 has no cancellation (an unknown makes the assignment itself undetermined, step 4). A combination is selected only if it ranks determinably first against every other combination.

   **Outcomes**: `none` (`k = 0`); `selected`; **`blocked`** (`FORCED_DROP_BLOCKED`) — evidence is sufficient to establish that there are not enough legal non-protected drops, i.e. `droppable + insufficient-evidence players < k`; **`undetermined`** (`FORCED_DROP_UNDETERMINED`) — evidence is insufficient to choose a legal deterministic combination: `k > 0` and any post-trade active player on that side has insufficient protection evidence (and the side is not demonstrably blocked), or no combination ranks determinably first. When `blocked` or `undetermined`: no selected forced-drop set (`dropped: null`), no final post-trade after-state valuation for that side (`after` lineup, `starter_total`, `depth_total` `null`), `starter_change`/`depth_change` `null`, and `diagnostics[]` explaining why (required `k`, candidates, excluded players with protection reasons or insufficient-evidence cause, the key and players behind each undetermined comparison). Caller-selected drops are a future extension.
6. **Starter change** = after − before `starter_total` when both are determined; otherwise `null`. Also `null` if a relevant game has kicked off (lock unverified).
7. **Depth change** is computed from actual before/after bench membership (active players not assigned a starter slot), including retained players that move between starter and bench: `Σ_after-bench max(0, VOR) − Σ_before-bench max(0, VOR)`. A player's unknown VOR cancels only when that same player is on the bench both before and after, so the contribution is demonstrably identical on both sides of the delta. Any other unknown contribution (traded, received, forced-dropped, promoted or demoted player) ⇒ `depth_change: null`. Undetermined bench membership (step 4) ⇒ `null`. **Absolute totals and deltas are distinct**: `depth_total` is `null` whenever any bench member's VOR is unknown, even when `depth_change` is known through cancellation. Unknowns are never counted as zero.
8. **Package status**: if either side is `blocked`, the package is `blocked`; otherwise if either side is `undetermined`, the package is `withheld`. In both cases diagnostics for both rosters are preserved; a side that resolved keeps its per-side results as diagnostics, but the package is not a completed evaluation. Only when both sides resolve is the status `evaluated`.
9. **Legality** is conditional: results describe legality under known roster rules (`legality: "conditional_known_rules"`). Platform transaction locks and deadlines are not available from provider data, so no result claims verified platform executability.
10. **Positional context**: before/after positive-VOR counts vs `eligible_starter_demand` per position (Superflex QB demand, TE premium via scored values, dual eligibility at best single VOR). Context only; no weight.
11. Components are reported separately per roster. Owner decision: no combined fairness score and no winner/loser verdict; a future combined policy (e.g. anything like add/drop's `0.25/0.10` net formula) needs its own design and validation.

## Assets and capabilities

- First wave supports `player` assets only. `draft_pick` and `faab` ⇒ `UNSUPPORTED_ASSET` with the capability reason. Pick holdings from Sleeper are transaction-history based, so pick ownership and pick values are not inferred.
- Provider-specific facts enter only through `TradeContext`; `lib/trade/*` imports no provider transport, no `lib/sleeper.js`, no `lib/derive.js`.
- ESPN live remains disabled; the evaluator works on an injected offline ESPN context in tests only.
- Signals, market attention and Sleeper add-interest are not read by the evaluator and are not protection evidence. Pickup Rating is unchanged.

## Computation and delivery

The evaluator is a pure function over an in-memory `TradeContext`. For side `s` and reserve allocation `a` (one allocation when no reserve slot is verified), let `n` be the forced-drop candidates and `k` the required drops; that allocation has `C(n, k)` candidate combinations (`C(n, 0) = 1`). Neither `C(n, 1) = n` nor `C(n, 2) = n(n−1)/2` bounds the other in general (for `n < 3`, `C(n, 2) < C(n, 1)`). Lineup solves per evaluation: 2 baseline before-solves (one per side) plus `Σ_s Σ_a C(n_{s,a}, k_{s,a})` after-solves, each combination's after-state requiring one solve. With `k ≤ 2` and typical rosters (e.g. `n = 15` ⇒ at most 105) this stays small. Nothing is added to `/api/decision-support`, `/api/snapshot` or `/api/chat/*` in the first wave. A later, separately approved task may add a lazy GET endpoint with its own schema (no persistence, identity-keyed cache); that task also wires authoritative protection evidence from the internal contexts.

| Case | V04-01 core unit tests | V04-02 adversarial suite |
|---|---|---|
| 1-for-1, 2-for-1, 1-for-2, 2-for-2 | basic | both sides, lineup reassignment |
| Out-of-scope shapes (3+ from a side, empty side, 3 rosters) | error codes | crafted proposals |
| Forced drops for uneven packages | lexicographic key, canonical id order, explicit output | protected-only rosters, blocked, undetermined, ties; **full legal lineup with a negative-value starter vs a candidate leaving a starter slot empty — the fully filled lineup ranks first despite the lower raw total** |

| Unknowns | `null` propagation, lineup-relevant rule | unknowns on each side, cancellation only for same-player bench-both-sides, unknown absolute total with known delta, starter/bench swaps of retained players |

| Superflex QB scarcity | ✓ | 10-team SF/TEP synthetic fixture |
| TE-premium scarcity | ✓ | 10-team SF/TEP synthetic fixture |
| Dual-position players | one slot, best single VOR | swaps that change which slot they fill |
| Injured / reserve / IR / taxi | verified placement only, joint allocation | open slot but unverified eligibility, missing capability, injured player not auto-IR'd, traded reserve players, two incoming players competing for one verified slot |
| Uneven roster sizes / over-capacity | ✓ | before-trade over capacity |
| Incomplete assets (picks, FAAB) | error codes | capability combinations |
| Ownership / duplicates / same roster | ✓ | stale basis, crafted proposals |

| League formats | — | 10-team Superflex/TE premium and 12-team full PPR, **synthetic** fixtures modeled on those structures |
